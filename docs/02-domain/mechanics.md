# Mechanics — механики предметной области

> Уровень: **Что происходит**. Каждая механика описана как правило поведения системы, без имён классов. Статус: **Fact** — подтверждено кодом; **Spec-only** — есть в `docs_old/` спеке, в коде отсутствует; **Partial** — реализовано частично.

## M1. Черновик → валидация → публикация → версия (Fact)

1. Все правки в UI меняют **черновик** агента (один на агента). Фронтенд сохраняет черновик в браузере и с задержкой ~400 мс синхронизирует с сервером; при недоступном API работает офлайн.
2. **Валидация** (одинаковый набор правил на сервере и в UI) выдаёт issues трёх уровней: `error` блокирует публикацию; `warning` и `info` — нет. Список правил — [`algorithms.md` §A7](./algorithms.md#a7-валидация-документа-агента).
3. **Публикация** создаёт неизменяемый снимок документа с версией: первая — `0.1.0`, далее `patch+1` от последней публикации. Публикация никогда не редактируется и не удаляется (кроме удаления агента).
4. Перед сохранением и публикацией документ **нормализуется**: остаточный «граф поведения» (снятый эксперимент Behavior Graph) один раз сплющивается в `states[]`, служебные поля графа удаляются.

## M2. Закрепление версии за процессом (Fact)

- Новый Skill Run создаётся по **последней** публикации агента и запоминает её версию.
- Любое последующее событие для этого run (явный `skill_run_id`, возобновление ждущего run, ответ на действие) исполняется **по закреплённой** версии, даже если агент опубликован заново.
- Если закреплённой публикации нет (удалена вместе с агентом) — событие пропускается с предупреждением.

## M3. Что делает событие: маршрутизация к процессам (Fact)

Для входящего события runtime определяет **цели** в таком порядке:

1. Явный `skill_run_id` на событии → этот run (даже если он в `error`; `cancelled` игнорирует).
2. Иначе по correlation (`conversation_id`, затем `request_id`, затем `entity_id`) ищутся **активные** run (`waiting`/`running`), у которых **текущее состояние объявляет переход на `event.type`**. Все подходящие получают событие (fan-out).
3. Иначе выбираются Skills агента, у которых **начальное** состояние ждёт `event.type`; для каждого создаётся новый run. При входе через канал подсказка `skillId` и `defaultSkillId` сужают выбор (см. [`algorithms.md` §A4](./algorithms.md#a4-выбор-skill-для-нового-события)).

Следствия:

- Ожидание на `conversation_id` **не перехватывает** событие другого типа (кнопку), если состояние его не ждёт — так разнесены «чат» и «работа» на одном разговоре.
- Событие, которое никто не ждёт и никто не стартует, пропускается (для `web.state.changed` — подтверждается как обработанное).
- No-match на уже существующем run не переводит его в `error`: run остаётся в прежнем статусе.

## M4. Диспетчер человеческого акта (Fact, control plane)

Перед маршрутизацией **человеческий входящий акт** (без `skill_run_id`, не `action.*`, не `runtime.continue`) классифицируется относительно открытых работ разговора, фокуса и текста. Диспетчер делит скиллы агента на **разговорные** (начальное состояние ждёт `channel.message.received`) и **рабочие** (ждёт жест `ui.request.parse_requested` / `human.request.reviewed`).

| Класс | Когда | Эффект |
|---|---|---|
| `pass_through` | не человеческий акт, или тип не чат и не жест | без изменений |
| `resume` | жест, который ждёт рабочая run; фраза «разбери…» при ждущей разбор работе; «да/подтверди» при работе, ждущей review; короткий ответ (не вопрос) работе, ждущей чат | событию проставляется `skill_run_id` цели |
| `start` | жест или фраза с намерением (parse/review) без подходящей ждущей работы | фраза **переписывается** в событие жеста (`ui.request.parse_requested` / `human.request.reviewed`) с `entity_ids` из фокуса/текста |
| `amend` | «сначала…», «только…», «не трогай» при идущей работе и известных сущностях | отменить все рабочие run разговора, стартовать разбор по суженному набору |
| `cancel` | «стоп», «отмена», «нет» при идущей работе | отменить рабочие run (по сущностям фокуса или все), затем передать акт разговорному скиллу |
| `side_question` | всё остальное: вопрос, обычная реплика | передать разговорному скиллу (возобновить его ждущий run, если есть) |
| `underspecified` | «разбери это» без фокуса/сущностей; «сначала…» без сущностей | передать разговорному скиллу (ожидается переспрос) |

Решение фиксируется в `metadata.dispatch` события. **Spec-only / Partial:** настоящий `amend` (изменение живого run) отсутствует — реализован как cancel + start; `redirect` отсутствует; переписывание `event.type` противоречит правилу «событие — факт» (REVIEW).

## M5. Шаг автомата (Fact)

При доставке события в run:

1. В `vars` подмешиваются данные payload (`text` → `last_message`; `conversation_id`; прочие ключи — если не заданы) и correlation-поля; записывается `_last_event_id`.
2. Если у агента есть `web_client` и событие — не служебное, читается **снимок стола** и накладывается на `vars` (поля открытой сущности побеждают прежние значения).
3. В текущем состоянии ищется первый handler с совпадающим `event` и истинным `guard`.
4. Выполняются `actions` handler-а по порядку; каждый — отдельный Action Run; результаты сливаются в `vars`.
5. Меняется состояние (`history += to`), выполняются `onEnter` нового состояния.
6. Для каждой выполненной операции синтезируется `action.<id>.completed` с `payload.result` — и обрабатывается тем же шагом (цепочки до 64 событий). Это позволяет ветвиться guard-ами по результату.
7. Legacy: пустой `event` или `runtime.continue` в handler-е считается авто-переходом; после цепочки они «дожимаются» до блокировки или `final` (до 32 раз).
8. Итоговый статус: `final` → `completed`; иначе `waiting`; исключение → `error`; `needs_human` → `waiting` с остановкой цепочки.
9. Run сохраняется с проверкой `revision`; в журнал run пишется запись события (тип, payload, from/to, вызовы инструментов, признак «run создан»).

## M6. Операция как рецепт (Fact)

- Вход операции собирается из `vars` run: `request_id`, `message` (= `last_message`/`text`), `message_id`, `conversation_id` плюс все несистемные `vars`. `inputSchema` не применяется.
- Шаги выполняются **последовательно**. Для каждого: проверка дедлайна (`timeoutMs`), условие `when`, подстановка шаблонов в `input`, разрешение ссылки `tool` в инстанс, вызов команды с контекстом (`vars`, `skill_run_id`, `action_id`, `action_run_id`, `steps`).
- Результат шага доступен следующим как `steps.<id>.result`; все результаты сливаются в выход операции **и** в `vars` run.
- Неуспех любого шага прерывает операцию. Повторы: `retry.max_attempts` применяется и ко всей операции, и к каждой команде (при «временной» ошибке — таймаут/5xx/connection — с паузой до 2 с).
- При исчерпании попыток: `on_failure = needs_human` → операция `waiting`, run `waiting`; иначе операция `failed`, run `error`.
- События, которые вернули инструменты (например, `channel.message.sent`), собираются и публикуются в шину после обработки.

## M7. Долгоживущее ожидание и возобновление (Fact)

- Операции короткие: «отправить вопрос прорабу» завершается сразу; ожидание ответа — состояние Skill Run (`waiting`).
- Ждущий run не держит worker; он найдётся по `conversation_id`/`request_id`/`entity_id`, когда придёт событие нужного типа; выполняется по закреплённой версии.
- Рестарт worker безопасен: run восстанавливается из хранилища.

## M8. Человек в контуре (Fact / Partial)

- **`needs_human` (Fact):** операция с такой политикой при ошибке не валит процесс, а ставит run в `waiting`; в `vars` фиксируется `_last_action_run_id`. Продолжение — любое событие, которое ждёт текущее состояние (например, `human.request.reviewed`).
- **Жесты UI (Fact):** кнопка = событие с `intent` и `entity_ids`; диспетчер объединяет кнопку и фразу в одну семью работ.
- **Двойной эффект (Partial):** исходящее сообщение в веб-клиент несёт `text`, `meta.workspace_update` (патч стола), `meta.ui_proposal`, `meta.presence`. Патчи шлёт только тот рецепт, который так настроен (например, сценарий `parse_request`); независимого канала «предложение UI» нет.
- **Стол побеждает vars (Partial):** снимок стола накладывается перед каждым человеческим актом; но речь по факту `web.state.changed` не порождается автоматически.

## M9. Надёжная доставка (Fact)

- **At-least-once.** События идут через поток с consumer group; сообщение подтверждается после успешной обработки.
- **Дедупликация.** `event.id` добавляется в множество обработанных; повтор пропускается. Множество не очищается (REVIEW).
- **Сериализация.** Обработка берёт распределённую блокировку по ключу: `conv-skill:<conversation>:<skill>` когда известны оба (две реплики одному скиллу — по очереди; чат и разбор на одном разговоре — параллельно); иначе `run:<id>`, `entity:<id>`, `event:<id>`. TTL 30 с, ожидание до 5 с.
- **Оптимистичная блокировка.** Сохранение run требует совпадения `revision`; конфликт оставляет сообщение в очереди для повтора.
- **DLQ.** После `EVA_EVENT_MAX_ATTEMPTS` неудач сообщение переносится в поток `<stream>:dlq` с причиной и подтверждается.

## M10. Отмена (Fact)

Отмена run (API, диспетчер, архивация агента): статус `cancelled`, активные Action Run → `cancelled`, дальнейшие события игнорируются. Отменённый run не возобновляется.

## M11. Таймеры (Partial)

Запись «событие `timer.elapsed` для run в момент T» может быть создана и позже превращена в событие с `skill_run_id`. **Fact:** создать такую запись из конструктора невозможно (нет команды/поля), а проверка наступивших таймеров выполняется только после обработки другого события того же агента/скилла. Таймер как пользовательская механика — **не реализован**.

## M12. Наблюдаемость исполнения (Fact)

- История run: журнал событий (тип, payload, from→to, вызовы инструментов) + Action Run с вложенными Tool Execution.
- Логи вызовов инструментов: отдельная лента на агента с фильтрами по инструменту/credential, статистикой, экспортом; секреты маскируются.
- Метрики процесса worker: `events_processed`, `runs_active`, `action_failures` (in-memory, сбрасываются при рестарте).
- Сводки: по всем агентам (running/waiting/error/completed за 24 ч) и по агенту.
- **Replay (Partial):** повторное проигрывание журнала событий run с позиции — без защит от повторных побочных эффектов (admin/test).

## M13. Валидация входа команды инструмента (Fact)

Перед вызовом команды вход дополняется значениями по умолчанию из схемы команды и проверяется по типам полей. Режим задаётся настройкой: `strict` — ошибка валидации = ошибка команды; `warn` — предупреждение в лог и выполнение; `off` — без проверки. Та же проверка на этапе валидации агента даёт `invalid_step_input`.

## M14. Каналы как источники событий (Fact)

| Канал | Вход | Что становится событием |
|---|---|---|
| Telegram webhook | `POST /api/channels/telegram/{slug}` | `channel.message.received` с `conversation_id = tg:chat:<id>`, `text` |
| Telegram polling | фоновый `getUpdates` по каждому credential | то же; offset хранится отдельно на credential |
| Веб-клиент | `POST /api/channels/web/{slug}/events` с Bearer = `inbound_api_key` | событие типа `type` (по умолчанию `channel.message.received`) с `conversation_id = sessionId`, `actor_id→user_id`, `focus`, `intent`, `entity_ids`; снимок акта кешируется |
| Прямой API | `POST /api/runtime/runs`, `/runs/start`, `/events` | синхронная обработка без шины (dev/test) |

Исходящие: `telegram.send_message` → Bot API (+ событие `channel.message.sent`); `web_client.send_message` → `POST {base}/eva/messages` (+ копия в outbox разговора, доступна клиенту через `GET …/sessions/{id}/outbox`).
