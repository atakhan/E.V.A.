# Research questions — открытые вопросы проекта

> Уровень: **Зачем / Что**. Вопросы, которые проект сам себе поставил и не закрыл (по `architecture/*.md` §29–30, `docs_old/*_SPEC` «Открытые вопросы», `INTERACTION_NOTES_ARCHITECTURE_REVIEW.md` §14–17) плюс вопросы, вскрытые при исследовании кода. Технические дефекты — не здесь, а в [`REVIEW.md`](../REVIEW.md).

## A. Концептуальные

**A1. Универсальность ядра.** Достаточно ли `Agent / Skill / Action / Tool / Event` для процессов, не похожих на снабжение (`agent_architecture_v1.md` §30)? Проверочный эксперимент — выразить `negotiate_supplier` и `process_invoice` без новых сущностей — **не проведён**. Пока доказано: `process_foreman_request` (demo), `razgovor` (диалог), `process_supplier_request` (жесты UI).

**A2. Planner.** Кто решает, *какие* процессы вообще нужно запустить (а не *как* выполнить один)? Варианты из §23: системный механизм runtime, Planner-Skill, внешний слой. Решение не принято; диспетчер актов (см. B) — не планировщик, он классифицирует один акт.

**A3. Память агента.** Memory — Tool с командами `search/propose/store` (§19–20), реализация (Entity Graph, pgvector) не определена. В коде есть только манифест `memory` без исполнения.

**A4. Reflection как обычный Skill.** Гипотеза §22: если рефлексия агента (анализ истории исполнения → кандидаты в память) выражается тем же конструктором, ядро универсально. Требует Tools `logs`/`memory` — не начато.

## B. Слой взаимодействия (человек ↔ агент)

Канон — `docs_old/INTERACTION_SPEC_v0.1.md`; честная приёмка — `INTERACTION_NOTES_ARCHITECTURE_REVIEW.md` §14: **2.5 из 6** критериев.

**B1. Якорь уточнения на сущности (Q4).** Вопрос агента должен быть виден и на карточке, и в чате, и закрываться любым ответом. Сейчас: «да» трактуется как review, если есть любая work-run (слишком широко); короткий ответ («мешки») не доходит до работы, если её состояние не ждёт `channel.message.received`.

**B2. Стол побеждает vars (Q6).** После ручной правки количества агент должен говорить новую цифру. Снимок стола подмешивается в `vars` перед обработкой (`runtime/desk.py`), факт `web.state.changed` принимается, но речь по этому факту не порождается — зависит от того, читает ли опубликованный рецепт стол.

**B3. amend ≠ cancel + start.** «Сначала Север» реализовано как отмена пакета и запуск суженного; история старого run теряется. Нужен ли настоящий amend (изменение очереди живого run)?

**B4. Event = факт vs rewrite диспетчера.** Диспетчер переписывает `event.type` (`channel.message.received` → `ui.request.parse_requested`) — единственное место, где код **спорит** с каноном Event (R10.3). Целевая форма — потреблять `DispatchDecision`, не переписывать событие. Сроки не определены.

**B5. Актёр и конфликты (R9.2).** Два человека на одном столе: last-write-wins запрещён спекой, но правила конфликтов не определены; в коде актёр — строка `user_id`.

**B6. Входящее извне на стол (R1.3).** Telegram-сообщение не входит в контракт акта (нет `focus`, `intent`); мир «стучится» только через веб-клиент.

## C. Runtime

**C1. Статусы Skill Run.** Спека: `CREATED → RUNNING → WAITING → … → COMPLETED | FAILED | CANCELLED`. Код: `running | waiting | completed | cancelled | error` без `created`. Нужен ли `created` как отдельная фаза?

**C2. Таймеры как первоклассный источник событий.** Инфраструктура `timer_schedules` + `RuntimeScheduler` есть, но ни один Skill/Action не может поставить таймер (нет команды/признака в DSL), а срабатывание проверяется только после обработки другого события того же агента. Как таймер должен выражаться в конструкторе?

**C3. Истечение run (`expires_at`).** Поле хранится, но не проверяется. Что должно происходить по истечении: `error`, `cancelled`, событие `timer.elapsed`?

**C4. Горизонтальное масштабирование worker.** Один consumer `worker-1`; lock `conv-skill:*` через Redis SET NX. Достаточно ли этого для нескольких реплик, и кто перераспределяет PEL при падении?

**C5. Параллельные шаги recipe.** ACTIONS_SPEC §13 / RUNTIME §24 — отложено. Нужны ли группы параллельных шагов, или достаточно последовательности?

**C6. Контракт входа Action.** Сейчас вход Action строится из `vars` run (`build_action_input`), а не из `inputSchema`; результаты шагов пишутся обратно в `vars`. Должна ли `inputSchema` стать нормативной (валидация/изоляция)?

## D. Tools

**D1. Семь каталожных типов без исполнения** (`memory`, `context`, `crm`, `catalog`, `web_search`, `files`, `saby`): roadmap, плагины извне или мусор каталога? В материалах не определено.

**D2. Tool SDK для внешних разработчиков.** `tools/scaffold.py` генерирует пакет, но регистрация остаётся ручной (`builtin_tools.py` + `definition_loader.py`). Нужен ли динамический plugin-механизм?

**D3. Tool и MCP** (TOOLS_SDK_SPEC §32) — обсуждалось как возможное направление; кода нет.

## E. Конструктор

**E1. Guards и `when`.** Guard — узкий язык (одно сравнение, `.length`). Хватит ли его реальным процессам (AND/OR, функции)? Связанный дефект областей видимости — в REVIEW.

**E2. Валидация на двух сторонах.** `validateAgent.ts` и `validate_agent.py` — два независимых порта одних правил. Оставлять дубль или сделать backend единственным источником (как сделано с каталогом Tools)?

## F. Эксплуатация

**F1. Миграции схемы.** `EVA_AUTO_MIGRATE` = `create_all` + `ALTER TABLE … IF NOT EXISTS` в `app/deps.py`; Alembic присутствует как заглушка без ревизий. Когда перейти на управляемые миграции?

**F2. Mult-environment секреты.** Infisical пути в `Makefile` (`/eva-postgres`, `/backend-environmet`) расходятся с шаблонами в `infisical/*/` и README. Какая раскладка каноническая?
