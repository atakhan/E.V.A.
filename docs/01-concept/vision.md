# Vision — что такое E.V.A. и зачем она существует

> Уровень: **Зачем**. Без кода и архитектуры. Источники: `architecture/agent_architecture_v1.md`, `architecture/backend_architecture_v1.md`, `docs_old/*_SPEC_v0.1.md`, `README.md`, git history (28 коммитов, 2026-08-25 … 2026-09-18).

## Одной фразой

**E.V.A. (Engine for Versatile Agents)** — конструктор и исполняющая среда ИИ-агентов: человек визуально проектирует поведение агента как набор конечных автоматов, а runtime надёжно исполняет это поведение, реагируя на события внешнего мира.

> «Человек проектирует поведение агента, а runtime исполняет это поведение.» — `architecture/agent_architecture_v1.md` §1

## Откуда взялся проект

**Fact.** Проект вырос из проектирования конкретного ИИ-агента для **снабжения** в строительной компании (прораб пишет заявку на материалы в Telegram, агент разбирает её, уточняет, подбирает позиции по каталогу, работает с поставщиками и счетами). В процессе стало ясно, что большая часть архитектуры не относится к снабжению, и была принята цель сделать универсальную систему, где «ИИ снабженца» — первый сложный пример агента на общем фундаменте.

> «Мы больше не проектируем „ИИ снабженца“. Мы постепенно проектируем язык и runtime для описания поведения ИИ-агентов.» — `architecture/agent_architecture_v1.md`, итог

**Fact.** Снабженческий контекст остаётся видимым в коде: сценарии-шаблоны `foreman` / `supplier` / `supplier-agent`, события `request.*`, `invoice.received`, `supplier.reply.received`, демо-эвристика «грибки → уточнить» в LLM-заглушке, интеграция с внешним веб-клиентом `ai_supplier` (соседний проект в этом же workspace).

## Какую проблему решает

1. **Поведение агента должно быть явным, а не «зашитым» в промпты или код.** Решение — декларативная модель: Skill (процесс) = конечный автомат из состояний и переходов по событиям; переходы вызывают Actions (операции); Actions собираются из Tools (технических возможностей) по рецепту.
2. **Процессы с людьми длятся часами и днями.** Агент отправил уточнение прорабу и ждёт ответа. Решение — долгоживущие **Skill Run**: состояние сохраняется, worker освобождается, ответ через сутки возобновляет тот же процесс.
3. **Несколько параллельных дел на одном разговоре.** Человек в веб-клиенте одновременно ведёт диалог и даёт поручения кнопками. Решение (слой Interaction) — разговор ≠ работа; один разговор может иметь 0..N одновременно идущих Skill Run; акт человека сначала классифицируется диспетчером, а не «любое сообщение продолжает ждущий автомат».
4. **Внешний мир подключается единообразно.** Telegram, LLM-провайдер, бэкенд веб-приложения — всё это Tools с командами и событиями; FSM не знает, какой именно инструмент стоит за операцией.

## Основная идея (модель)

```text
Agent  = композиция Skills + Actions + Tools
Skill  = процесс класса задач; описывается FSM (states, events, guards)
Action = именованная операция; рецепт из команд Tools
Tool   = техническая способность (команды + события), без бизнес-логики
Event  = факт «что-то произошло»; не команда

Event → (Dispatcher) → Skill Run → FSM → Action → Tool → World → Event
```

Пять вопросов, на которые отвечают сущности (`agent_architecture_v1.md` §25):

| Сущность | Вопрос |
|---|---|
| Tool | Что агент *умеет*? |
| Action | Что агент *делает*? |
| Skill | *Как* агент решает класс задач? |
| State | *Где* сейчас процесс? |
| Event | *Что произошло*? |

Подробно — [`02-domain/overview.md`](../02-domain/overview.md).

## Две плоскости

- **Definition plane (конструктор):** человек создаёт агента в UI, редактирует Skills на FSM-холсте, собирает Actions, подключает Tools и credentials, валидирует и **публикует**. Публикация неизменяема и версионируется.
- **Runtime plane (исполнение):** события приходят из каналов, worker находит или создаёт Skill Run, интерпретирует FSM, исполняет Actions через Tools, сохраняет историю исполнения. Runtime читает только публикации, не черновики.

## Для кого

**Inference** (из UI, сценариев и соседних проектов workspace): внутренняя команда/компания, строящая прикладных агентов (снабжение, диалоговый ассистент для CRM-подобного веб-клиента). Публичных пользователей, мультитенантности и биллинга в коде нет.

## Текущее состояние (на 2026-09-18, последний коммит)

**Fact.**
- Backend: FastAPI + Postgres + Redis Streams; runtime worker; Telegram poller; 5 реальных Tool-реализаций (`llm`-stub, `polza_ai_llm`, `telegram`, `text`, `web_client`) и 7 типов только в каталоге без исполнения (`memory`, `context`, `crm`, `catalog`, `web_search`, `files`, `saby`).
- Frontend: Vue 3 SPA — список агентов, Overview с готовностью к публикации, FSM-холст Skills, редактор Actions/recipe, библиотека Tools и инстансов с credentials, логи вызовов, Runtime Cockpit (runs, timeline, cancel, simulate).
- Слой Interaction (диспетчер актов, snapshot стола, presence) реализован как **control plane**: честная приёмка — 2.5 из 6 критериев спеки (см. [`06-experiments/README.md`](../06-experiments/README.md)).
- Прежняя документация (нормативные спеки v0.1, заметки Interaction) лежит в `docs_old/` — это предыдущее поколение документации, полезное как справочник контрактов; расхождения с кодом зафиксированы в [`REVIEW.md`](../REVIEW.md).
