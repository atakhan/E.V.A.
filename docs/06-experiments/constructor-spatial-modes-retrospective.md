# Ретроспектива: пространственные режимы конструктора (хаб Евы → проект → агент → канал)

> Зафиксировано 2026-11-06 по итогам серии итераций над UI проектов/конструктора.
> Разделение: **Fact** — что есть в коде и переписке; **Interpretation** — оценка качества и процесса.

---

## 1. Что сделали (Fact)

### Режимы пространства

Собрана связная лестница режимов на одном маршруте `/projects/:projectSlug?/:agentSlug?`:

| Режим | Центр | Сателлиты |
|-------|--------|-----------|
| Стол Евы (хаб проектов) | Ева | проекты на верхней орбите |
| Конструктор Евы | hub агента `eva` | каналы / мир конструктора |
| Стол проекта | рантайм-агент проекта | агенты проекта |
| Конструктор агента | hub выбранного агента | каналы, адреса |
| Канал / слой канала | карточка канала или action | адреса, дуга действий, панели |

Переходы задуманы как **пространственные**, а не как смена страниц: иконка летит, сателлиты схлопываются/вылетают, hub конструктора подхватывает полёт.

### Принцип анимации (сформулирован поздно, применён задним числом)

> В каждом переходе все элементы обеих режимов начинают анимацию одновременно. Всё в один заход.

До аудита большинство переходов были **фазами** (`await` collapse → потом flight → потом reveal). После аудита:

- тайминги сателлитов выровнены с `DESK_MOVE_MS`;
- stagger убран как блокирующая фаза, затем частично возвращён только как лёгкий «физический» каскад на burst;
- handoff: сначала целевая иконка, на следующем кадре снимается летящая (против мерцания);
- фокусный объект не схлопывается в якорь вместе с остальными (иначе полёт ломается);
- на столе проекта раскладка сателлитов приведена к **packed**-алгоритму хаба Евы.

### Объём изменений (на момент ретро, незакоммиченный пласт поверх `dev`)

Ориентиры по `git status` / `diff --stat` и размеру ключевых файлов:

- **~19 затронутых файлов** в основном пласте + новые `ProjectsDesk.vue`, `projectsHubLayout.ts` (+ тесты);
- порядка **+1100 / −150** строк в уже отслеживаемых файлах (без учёта всего `ConstructorView`, который рос раньше);
- ядра режимов: `ProjectsListView.vue` (~790 строк), `ProjectDeskView.vue` (~840), `ConstructorView.vue` (~1850), раскладки `projectsHubLayout` / `deskLayout`.

По смыслу это не «пара анимаций», а **сквозной UX-слой**: роутинг, платформенный агент Ева, два стола, орбиты, полёты, handoff в конструктор, канальные слои, выравнивание плотности сателлитов.

## 2. Оценка качества (Interpretation)

### Что получилось сильно

1. **Единая пространственная метафора** — режимы читаются как масштабы одного стола, а не как набор экранов. Это согласуется с `docs/01-concept/spatial-model.md` и конструкторской осью мира.
2. **Принцип «один заход»** — когда его наконец назвали явно, он стал хорошим критерием приёмки: нарушения находились по `await`-фазам, а не по вкусу.
3. **Итеративная калибровка глазами** — мерцание, двойники иконок, «дерганье» агентов ловились на реальном прогоне; правки точечные и проверяемые.
4. **Раскладка** — packed-орбита хаба Евы оказалась удачной; перенос на стол проекта убрал ощущение «разреженности» без новой метафоры.

### Где качество ещё хрупкое

1. **Сложность в view-слое.** `ProjectsListView` / `ProjectDeskView` держат stage-машины, измерения DOM, handoff и флаги вроде `hubClear` / `deferSatelliteReveal` / `exitingToHub`. Работает, но порог входа высокий; легко снова сломать handoff одной перестановкой присваиваний.
2. **Принцип появился после реализации.** Сначала построили красивые, но последовательные переходы; потом привели к принципу. Цена — несколько кругов регрессий (полёт Евы, twin runtime, burst агентов).
3. **Дублирование логики.** Похожие enter/leave и handoff в двух view + частично в `ConstructorView`; раскладки хаба и стола теперь алгоритмически близки, но всё ещё два файла.
4. **Мало автоматических тестов на motion.** Есть unit-тесты раскладки; нет тестов на порядок handoff / «нет кадра без иконки». Регрессии ловятся только руками.
5. **Незакоммиченный пласт.** Большой объём живёт в working tree — риск потерять связность истории, если не оформить осмысленным коммитом/серией.

### Итоговая оценка

| Ось | Оценка | Комментарий |
|-----|--------|-------------|
| Объём | высокий | сквозной UX + роутинг + раскладки + motion |
| Концептуальная ясность | высокая | режимы и лестница масштабов понятны |
| Инженерная чистота | средняя | работает, но stage-машины перегружены |
| Соответствие заявленному принципу motion | хорошее после доводки | изначально не соблюдалось |
| Устойчивость к регрессиям | средняя− | сильная зависимость от ручного прогона |

**Вердикт:** для продуктового ощущения пространства — заметный шаг вперёд; для долгосрочной сопровождённости — нужна следующая итерация на упрощение API переходов (один «motion coordinator», меньше флагов, тесты handoff).

## 3. Рефлексия о процессе (Interpretation)

### Как мы работали

1. **Сначала — конкретные фичи и ощущение**, не абстрактный рефакторинг: иконки на дуге, полёт как у runtime→agent, хаб Евы вместо списка.
2. **Приёмка — визуальная и пошаговая.** Пользователь называл артефакт («дергается», «копия в конечной точке», «блик»), агент искал причину в порядке кадров / collapse / opacity transition.
3. **Принцип как контракт появился вовремя, но не в начале.** Запрос «проверь каждый переход на принцип» перевёл работу из «сделай красиво» в «приведи к инварианту» — это сработало лучше вкусовщины.
4. **Ошибки агента были предсказуемого типа:** слишком последовательные `await`; схлопывание фокусного объекта вместе с сателлитами; показ целевой иконки до прилёта; fade opacity на handoff. Почти все — про то, что **две визуальные сущности делят одно место в пространстве и времени**.

### Что в общении помогало

- Короткие наблюдения вместо общих «не нравится анимация».
- Явные принципы («всё в один заход», «от рантайма с физикой»).
- Сравнение двух существующих решений (хаб vs стол) перед унификацией — быстрее, чем изобретать третье.
- Цикл: гипотеза → правка → «да, лучше, теперь вот это» — без потери контекста режима.

### Что мешало / можно улучшить в следующий раз

1. **Сначала инвариант, потом реализация переходов.** Имея принцип one-pass и правило handoff («сначала цель, потом убрать летящую; opacity snap») до кода, меньше кругов.
2. **Чеклист приёмки переходов** (туда/обратно × каждый режим): нет twin, нет blank frame, нет jerk orbit→anchor→orbit, фокус не в collapse.
3. **Не смешивать в одном заходе** «добавить режим» и «переписать все тайминги» — либо изолировать motion-слой раньше.
4. **Фиксировать принцип в коде/доке сразу**, как только он назван (сейчас он в основном живёт в `deskMotion.ts` комментариях и в этой ретроспективе).

## 4. Чему научились (выводы)

1. В пространственном UI **главный баг — не кривая кривая Безье, а конкуренция двух иконок за одно место**.
2. Collapse сателлитов обязан **исключать фокус**, иначе полёт уничтожается собственной орбитой.
3. Packed-дуга читается «живее», чем равномерный stretch на весь `SPREAD`, особенно при малом числе объектов.
4. Визуальный принцип полезнее набора таймингов: тайминги подстраиваются под принцип, а не наоборот.
5. Совместная работа шла лучше всего, когда пользователь давал **локальный симптом + желаемую физику**, а агент отвечал **минимальным диффом с проверкой соседних переходов**.

## 5. Инженерная рефлексия: код, костыли, дубли, оптимизация (Interpretation)

Взгляд «как кодеры» на то, что осталось после доводки UX. Оценки субъективны; якоря — текущие файлы и паттерны в `projects/` + `ConstructorView`.

### 5.1. Где мы накопили сложность

| Зона | Симптом | Почему так вышло |
|------|---------|------------------|
| `ProjectsListView.vue` (~790 строк) | stage + ~15 refs (`hubClear`, `iconSnap`, `evaSnap`, dual flight, held slugs…) | каждый баг handoff лечился флагом, а не моделью перехода |
| `ProjectDeskView.vue` (~840) | почти зеркальная stage-машина enter/leave + `wait`/`frame`/`waitForConstructor` | копипаст с хаба вместо общего модуля |
| `ConstructorView.vue` (~1850) | канал/слой/flight живут в том же монолите | третий экземпляр той же идеи «полёт + сателлиты» |
| `deskLayout.ts` ≈ `projectsHubLayout.ts` | алгоритм packed-орбиты продублирован 1:1 | унифицировали поведение, не код |
| DOM-измерения | `document.querySelector("[data-*-desk]")` + `getBoundingClientRect` в циклах кадров | быстро и работает; хрупко к структуре шаблона |

**Fact:** в двух view суммарно десятки `await wait|frame|nextTick` на переходы; `hubClear` одновременно значит «прозрачный хаб», `deferSatelliteReveal` и `exitingToHub`.

### 5.2. Костыли и хаки (честный список)

1. **`hubClear` как швейцарский нож** — один boolean оркестрирует z-index, clear backdrop, скрытие Евы/FAB/nav, парковку runtime и семантику leave. Читается только если помнишь историю багов.
2. **`heldProjectSlug` / `heldAgentSlug`** — костыль против того, что роут очищает slug до конца leave-анимации. Правильнее: анимация владеет «уходящим» контекстом явно (или navigation guards / view-transition state).
3. **Handoff через «покажи A → frame → спрячь B»** — правильный визуально, но размазан императивно в каждой `enter*`/`leave*`. Нет одной функции `handoffSeat({ from, to })`.
4. **Snap-флаги (`iconSnap`, `evaSnap`, `everRevealed`)** — локальные костыли против CSS «анимируй из неправильного first paint». Сигнал, что transition API слишком низкоуровневый для наших инвариантов.
5. **Прозрачный хаб поверх стола** вместо портала/единого overlay-flyer — работает, но два полноэкранных слоя и z-fight логика.
6. **Constructor ready + timeout 800ms** — гонка «когда hub смонтировался»; remain-glide компенсирует опоздание. Хрупкий договор между parent и `ConstructorView`.
7. **Два имени одной идеи сателлитов** — `hubSatellites` / `deskSatellites` / `satellites` (constructor) / `channelSatellites` / `layerSatellites`: одна метафора, пять ручек.

### 5.3. Дубли (структурная несогласованность)

```text
enter/leave + measureFocus + wait/frame + waitForConstructor
    ├── ProjectsListView
    ├── ProjectDeskView
    └── (частично) ConstructorView channel/layer

packed orbit layout
    ├── projectsHubLayout.ts   (константы под подписи проектов)
    └── deskLayout.ts          (константы под иконки агентов)  ← почти copy-paste

ProjectsDesk.vue ↔ ProjectDesk.vue
    placeStyle / orbitTransition / iconStyle — близнецы
```

**Направление:** один `useDeskMotion()` (token, wait, frame, handoff, flight state) + один `layoutPackedOrbit({ minChord, maxSpread, … })` + один `OrbitDesk` с слотами.

### 5.4. Читабельность

- Переходы — **процедурные сценарии**, а не декларативное описание «fromMode → toMode → actors». Новый человек не видит инвариант «один заход», пока не прочитает ретро/правило.
- Смешение **routing state**, **DOM measure**, **CSS transition orchestration** и **бизнес-загрузки проекта** в одном SFC.
- Магические числа всё ещё живут рядом с именованными (`EVA_ICON = 96`, stagger 32/200) — лучше собрать в `deskMotion` / layout constants.
- Комментарии в горячих местах хорошие («Land under flyer…»), но они компенсируют отсутствие API.

### 5.5. Производительность

Сейчас при типичной нагрузке (десятки сателлитов) узких мест, скорее всего, нет. Риски на рост:

| Риск | Где | Что делать |
|------|-----|------------|
| Лишние layout thrash | `measure*` + `getBoundingClientRect` на каждом handoff/кадре | мерить один раз на старте pass; кэшировать desk rect |
| Глобальный `querySelector` | каждый measure | держать `ref` на board / icon, не искать по документу |
| Несколько `ResizeObserver` | desk + view + documentElement | один observer на desk root, событие вверх |
| Одновременные CSS transitions на N сателлитах | burst | уже ок; не возвращать тяжёлый stagger + filter/shadow на каждый |
| Монтирование `ConstructorView` (~тяжёлый) на каждый вход | enterEva / enter agent | держать тёплый instance или lazy + скелет hub только для полёта |
| Два fullscreen слоя (hub + desk) в DOM | `hubClear` pass | overlay-flyer вместо второго opaque дерева, когда можно |

Не оптимизировать «на глаз» до профиля: сначала структурный вынос motion, потом точечный measure cache.

### 5.6. Как бы оптимизировали структуру (целевой скелет)

```text
features/projects/
  motion/
    useDeskMotion.ts      # token, wait, frame, reducedMotion
    handoff.ts            # landTarget → nextFrame → dropFlyer
    flight.ts             # { dx, dy, scale } helpers
  layout/
    packedOrbit.ts        # shared algorithm
    hubConstants.ts
    deskConstants.ts
  components/
    OrbitBoard.vue        # shared placeStyle/iconStyle
  views/
    ProjectsListView.vue  # routing + composition only
    ProjectDeskView.vue
```

Инвариант из [`spatial-ui-principles.md`](../01-concept/spatial-ui-principles.md) тогда живёт в `handoff.ts` / `useDeskMotion`, а не в устной традиции.

### 5.7. Приоритеты рефакторинга (практично)

1. **Высокий ROI / низкий риск:** слить `deskLayout` + `projectsHubLayout` в параметризованный `packedOrbit`.
2. **Высокий ROI / средний риск:** `useDeskMotion` + общий `handoffSeat`; убрать копипаст wait/frame/ready.
3. **Средний ROI:** заменить `hubClear`-мультифлаг на явный `TransitionPass { phase, flyer, seat }` или маленький state machine.
4. **Средний ROI:** refs вместо `querySelector` для measure.
5. **Ниже / когда будет боль:** тёплый `ConstructorView`, overlay-flyer, тесты порядка handoff.

Не делать большим bang-rewrite: резать вертикальными тонкими PR, сохраняя чеклист приёмки переходов.

## 6. Открытый хвост

- Вынести общий motion/handoff helper из двух view.
- Объединить или параметризовать `projectsHubLayout` / `deskLayout` (алгоритм один, константы разные).
- Тесты на handoff-инварианты (хотя бы через чистые функции порядка шагов).
- Закоммитить пласт осмысленными коммитами (режимы / motion principle / layout unify).
- Прогнать полный ручной чеклист всех переходов ещё раз после коммита (регрессии handoff чувствительны).
- (из §5) Развести `hubClear` на явные роли; refs вместо глобального querySelector; не трогать perf без профиля.
