# E6. Обратимость языка навыка (R1 / R2) — сравнение поведения

> Статус: **проведён на бумаге + разбор runtime**, 2026-10-13. Не автоматический харнесс. Следует за [`E5-skill-language-paper-test.md`](./E5-skill-language-paper-test.md). Не смешивать с уровнем агента (тот — E8).

```text
Experiment:   Для набора автоматов построить человеческое представление по нотации E5,
              затем восстановить FSM по правилам R1/R2 и сравнить исходный и восстановленный
              автомат по поведению, а не по тексту/именам состояний.
Hypothesis:   R1 и R2 — вид, а не компиляция: round-trip сохраняет наблюдаемое поведение
              Skill Run (переходы при событиях, точки ожидания, финалы, ветки по результату
              действия), даже если имена промежуточных состояний и запись on_enter vs
              actions-на-переходе различаются.
Purpose:      Закрыть (или опровергнуть) главный риск E5 до проектирования навыка с нуля
              и до пространства агента: не закрепляем ли мы скрытые соглашения и потери
              семантики под видом «красивого» языка.
Material:     letter_agent_document / foreman_agent_document + мини-автоматы K4–K8.
              Правила исполнения: fsm_engine.apply_transition, skill_runner.handle
              (needs_human / error — Fact по коду).
Procedure:    1) Кейс = FSM + сценарии. 2) Человеческий вид. 3) Восстановление каноном
              R1/R2. 4) Сравнение поведения. 5) Совпало / разошлось / новое правило.
```

---

## 1. Что сравниваем (поведение, не текст)

| Наблюдение | Пример |
|---|---|
| Текущее состояние / final | run в `waiting_for_*` или `completed` |
| Какие actions вызваны и в каком порядке | `parse_request` затем `clarify` |
| Какой тип события «ждёт» run | resume только на `channel.message.received` |
| Какая ветка сработала | `needs_clarification == true` → уточнение |
| Где отдыхает run при `needs_human` | см. факт runtime ниже |
| Где остаётся run при жёсткой ошибке действия | факт runtime ниже |

**Факты runtime (не спека), от которых зависит сравнение:**

1. Порядок перехода (`fsm_engine.apply_transition`): **сначала** все `transition.actions`, **потом** `record_state(to)`, **потом** `on_enter` нового состояния.
2. При `needs_human` действие **не** бросает исключение: ставит `_needs_human`, возвращает данные; переход **всё равно** меняет состояние и запускает `on_enter`.
3. `skill_runner` после шага, если `_needs_human`, ставит `waiting` и **не дренирует** `action_completions` (события `action.*.completed` в этом такте не обрабатываются).
4. При жёстком `fail` действия: `RuntimeError` **до** смены состояния, если действие на переходе; если действие в `on_enter` — состояние **уже** сменено.

**Провал:** нельзя однозначно восстановить; поведение расходится; появляется конструкция без формы в FSM.

## 4. Разбор кейсов

### K1. `compose_letter`

**Исходный FSM (сжато):**

```text
queued --[ui.request.parse_requested | compose_draft]--> waiting_for_human
waiting_for_human --[human.request.reviewed | decision==approve | record_letter]--> recorded (final)
waiting_for_human --[… | correct | note_correction]--> waiting_for_human
waiting_for_human --[… | defer | defer_letter]--> waiting_for_human
```

**Человеческий вид** — как в E5 §2.

**Восстановление каноном:** тот же граф. Шаг `compose_draft` без обстоятельств на результате → действие на переходе, без промежуточного состояния (R1 не требует свёртки). Петли ожидания — явные.

**Сценарии:**

| Сценарий | Исходный | Восстановленный |
|---|---|---|
| повод → черновик → одобрить | `queued→waiting→recorded`, actions compose→record | то же |
| повод → править → одобрить | петля в `waiting`, note затем record | то же |
| отложить | петля + defer | то же |

**Итог: совпало** на сценариях решения человека.

**Оговорка (связь с K5):** если `compose_draft` вернёт `needs_human`, run окажется в `waiting_for_human` *до* решения человека, с тем же типом ожидаемого события `human.request.reviewed`. В языке E5 это неразличимо с «ждать решения». Скрытое соглашение + дыра языка, не расхождение round-trip текста FSM.

### K2. Прораб как в коде (`on_enter: clarify`)

**Исходный:**

```text
NEW --[msg | parse_request]--> ANALYZING
ANALYZING --[parse.completed | needs | ]--> CLARIFYING   on_enter: [clarify]
ANALYZING --[parse.completed | !needs | ]--> READY (final)
CLARIFYING --[clarify.completed | ]--> WAITING_FOR_FOREMAN
WAITING --[msg | same conversation]--> READY
```

**Вид (E5):** шаг «Разобрать» с обстоятельствами; «Спросить» → «Ждать ответа».

**Восстановление по R1+R2 (канон — действие на переходе):** см. K3.

**Happy path (нужно уточнение, clarify ok, ответ):**

| | K2 исходный | |
|---|---|---|
| состояния | NEW→ANALYZING→CLARIFYING→WAITING→READY | |
| actions | parse, clarify | |
| ждёт | `channel.message.received` в WAITING | |

Совпадает с K3 по actions и финальному ожиданию; **число состояний другое** (CLARIFYING лишний для happy path) — по критерию E6 имена/лишние промежуточные **допустимы**, если поведение то же.

**Итог happy path: совпало** (с K3 по наблюдаемому концу).

**Fail / needs_human:** см. K3 — здесь как раз **расхождение форм**.

### K3. Прораб, канон R2 (clarify на переходе)

**Восстановленный канон:**

```text
NEW --[msg | parse_request]--> AFTER_PARSE          # R1: промежуточное после шага с ветками
AFTER_PARSE --[parse.completed | needs | clarify]--> WAITING
AFTER_PARSE --[parse.completed | !needs |]--> READY
WAITING --[msg]--> READY
```

(Имя `AFTER_PARSE` вместо `ANALYZING` — не важно. `clarify.completed` из WAITING — no-match, игнорируется; на happy path это не меняет исход.)

**Сравнение с K2:**

| Сценарий | K2 (`on_enter`) | K3 (действие на переходе) | |
|---|---|---|---|
| happy, нужно уточнение | отдых в WAITING после clarify.completed | отдых в WAITING сразу после clarify; completion ignored | **≈ совпало** |
| clarify → `needs_human` | отдых в **CLARIFYING** | отдых в **WAITING** | **разошлось** |
| clarify → hard fail | ошибка уже в **CLARIFYING** | ошибка ещё в **AFTER_PARSE** / ANALYZING | **разошлось** |

**Итог:** R2 как «читаем обе формы, пишем одну» **не сохраняет поведение** на путях ошибки и `needs_human`. На happy path — да.

**Следствие для правил:** канонизация `on_enter` ↔ actions-на-переходе **небезопасна** без явного учёта места отдыха. Либо:

- **R2′:** round-trip обязан сохранять, *в каком состоянии* run ждёт / ошибается → тогда `on_enter` и действие на переходе — **разные** записи, которые язык должен различать; или
- язык получает слово про «если не удалось / если нужно человеку» с привязкой к месту (это уже K5).

Пока фиксируем: **гипотеза E6 в части R2 опровергнута на fail-путях.**

### K4. Граница свёртки R1

**Исходный мини-автомат:**

```text
S0 --[msg | parse]--> S_PARSE
S_PARSE --[parse.completed | ok |]--> DONE
S_PARSE --[parse.completed | bad | ask]--> WAIT
S_PARSE --[timer.elapsed |]--> TIMEOUT (final)    # инородный обработчик
WAIT --[msg |]--> S0   # снова
```

Условие свёртки R1: «входят только переходы с действием X; выходят только `action.X.completed`». Здесь на `S_PARSE` есть `timer.elapsed` → **свёртка запрещена**.

**Вид:**

```text
→ Разобрать заявку
    … нельзя свернуть в «обстоятельства шага» …

→ Ждать: разбор заявки
    ждёт: результат разбора | таймер
    разбор ок     → готово
    разбор плох   → Спросить → Ждать ответа → (снова) Разобрать
    таймер        → готово: истекло
```

**Восстановление:** тот же граф с явным ожиданием. Поведение идентично.

**Итог: совпало.** R1 в форме «свёртка только при чистом условии, иначе явное ждать» — вид, не потеря.

### K5. `needs_human` на действии перехода

Возьмём фрагмент письма: `queued --[parse_requested | compose_draft]--> waiting_for_human`.

| Исход | Состояние | status | Что «ждёт» по FSM |
|---|---|---|---|
| compose_draft ok | `waiting_for_human` | waiting | `human.request.reviewed` |
| compose_draft `needs_human` | `waiting_for_human` | waiting | те же переходы! completions не дренированы |
| compose_draft hard fail | `queued` | error | — |

В нотации E5 оба успешных исхода пишутся одинаково: «→ Собрать черновик → Ждать решения». **Место и причина ожидания после неудачи действия в языке не выражены.**

Это не расхождение round-trip одного и того же FSM (граф тот же). Это **дыра языка** относительно наблюдаемого поведения runtime: человек не может сказать «если черновик не собрался — останься здесь / позови человека» отдельно от «жди решения по черновику».

Слово «если не удалось» из E5 §6 (таблица «слов нет у исполнения») частично про таймеры; про `needs_human` после действия — **есть у исполнения, нет у языка**. Добавлять слово сейчас = риск E1, пока не решим, как это выглядит в FSM однозначно (отдельное состояние? тот же waiting с другим смыслом?).

**Итог:** R1/R2 не сломаны как отображение графа; **критерий «язык покрывает наблюдаемое поведение» для K5 — нет.** Блокер для E7, если новый навык предполагает человеческое подтверждение внутри действия.

### K6. Два действия на переходе, ветка по второму

```text
A --[e | act1, act2]--> MID
MID --[action.act2.completed | good |]--> OK
MID --[action.act2.completed | bad |]--> FAIL
# action.act1.completed в MID — no-match
```

**Вид:**

```text
→ Сделать act1, затем act2
    нужно: …
    узнаёт: (от act2) good/bad
    good → готово: ok
    bad  → готово: fail
```

**R1′ (уточнение):** свёртка «обстоятельства шага» обобщается на *хвост* перехода: промежуточное состояние слушает `completed` **последнего** действия списка (или явно названного), а не обязательно единственного. `act1.completed` no-match — допустимо, если ветки не смотрят на act1 (результат всё же может лежать в `vars` — скрытое соглашение).

**Восстановление:** тот же граф. Happy/bad по act2 совпадают.

**Итог: совпало** при явном R1′. Риск: если когда-нибудь понадобятся ветки по act1 *и* act2 на одном промежуточном — нотация E5 этого ещё не умеет (два «узнаёт» подряд без второго ожидания). Пока не встретили — не вводим слово.

### K7. Два final

```text
W --[approved |]--> RECORDED (final)
W --[rejected |]--> CANCELLED (final)
```

**Вид:** `одобрил → готово: записано` / `отклонил → готово: отменено`.

**Восстановление:** два final. Поведение совпадает.

**Итог: совпало.** Нотация уже допускала `готово [: исход]`.

### K8. Возврат «снова разобрать» (исправленный D3)

```text
NEW --[msg | parse]--> AFTER_PARSE
AFTER_PARSE --[parse.completed | needs | ask]--> WAIT_ANSWER
AFTER_PARSE --[parse.completed | !needs |]--> READY
WAIT_ANSWER --[msg | parse]--> AFTER_PARSE      # снова разобрать, не сразу READY
```

**Вид:**

```text
→ Разобрать …
    нужно уточнение → Спросить → Ждать ответа
                          прораб ответил → Разобрать (снова)
    всё ясно → готово
```

**R3:** «снова» = переход в существующее место (AFTER_PARSE), не новый узел.

Round-trip сохраняет цикл. Guard-сантехника D1 снята (предполагаем pin runtime).

**Итог: совпало.**

## 5. Observed results

1. **R1 (свёртка чистого промежуточного / явное ожидание иначе)** на K1, K4, K6′, K8 — **держится** как вид: восстановленный граф ведёт себя как исходный на разобранных сценариях.
2. **R2 (канон «всегда действие на переходе»)** на K2↔K3 — **не держится** на `needs_human` и hard fail: меняется состояние отдыха / ошибки. Happy path совпадает.
3. **K5:** язык E5 **не различает** «жду результат действия / человека по политике действия» и «жду доменное событие в том же состоянии». Это не провал обратимости графа, а пробел покрытия поведения.
4. Скрытые соглашения E5 подтверждены как отдельные от обратимости: K1–K3 на них опираются; сами R1/R2 от них не зависят.
5. Новых слов без формы в FSM **не вводили**. Стоп-условие E1 не сработало.

## 6. Interpretation

- Главный риск «это второй Behavior Graph» для **R1** пока не подтвердился: свёртка локальна, обратима, при нарушении условия деградирует в явное ожидание (K4).
- **R2 в формулировке E5 слишком сильна.** `on_enter` и actions-на-переходе — не взаимозаменимый синтаксический сахар относительно runtime. Либо язык их различает, либо канон фиксирует одну форму *и* мы принимаем смену семантики fail-путей (плохо), либо fail-пути получают явные строки в языке (K5).
- Для перехода к E7: язык навыка можно пробовать на сценариях **без** `needs_human` внутри действия и без ставки на перепись `on_enter`→transition. Иначе сначала закрыть K5/R2′.
- Пространственная гипотеза («свой язык уровня + контракт») E6 **не доказала и не опровергла**; она лишь очистила, что можно обещать про отображение навыка ↔ FSM.

## 7. Уточнённые правила (черновик после E6)

| ID | Было (E5) | Стало |
|---|---|---|
| R1 | свёртка, если только X.completed | без изменений; иначе явное «ждать» (K4 ✓) |
| R1′ | — | несколько actions на переходе: обстоятельства по **последнему** (K6); иначе не сворачивать |
| R2 | читать обе формы, писать действие на переходе | **ослабить:** канон записи допустим только если fail/`needs_human` пути не важны *или* совпадают; иначе сохранять форму (`on_enter` vs переход) как часть поведения |
| R2′ (кандидат) | — | в языке различать «сделать по дороге в ожидание» и «сделать при входе в место» — только если E7 упрётся |
| R5+ (кандидат, K5) | — | не добавлять слово, пока нет однозначной FSM-формы для «действие позвало человека» |

## 8. Решение по критерию E6 и следующий шаг

| Вопрос | Ответ |
|---|---|
| Можно ли идти в E7 сразу? | **Условно да**, на навыке без `policy/on_failure: needs_human` у действий и без необходимости нормализовать чужие `on_enter`. |
| Что обязательно сказать в E7-брифе? | Контракт действия (`нужно`/`узнаёт`) объявить явно; не опираться на `last_message` и необъявленный payload. |
| Блокер полного «языка навыка» | K5 + ослабленный R2 — закрыть до того, как обещать автору «пишите только человеческим языком, всё остальное восстановится». |

**Рекомендуемый следующий ход:** короткий E7 на сценарии в духе письма (ожидание человека = доменное событие, не `needs_human` действия) *или* сначала мини-решение по K5 (как показать в нотации «действие не завершилось / нужен человек»). На `process_supplier_request` (E8) не переходим.

## Limitations

Сравнение вручную по таблицам переходов и чтению `fsm_engine`/`skill_runner`, без pytest round-trip. K6–K8 — синтетические мини-графы, не из репозитория. Не проверялись: параллельные ветки от двух `completed` на одном состоянии; отмена run; `runtime.continue`. Имена знания (R4) не валидировались исполнением.
