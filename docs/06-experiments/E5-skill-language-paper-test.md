# E5. Язык навыка без компилятора — проверка на бумаге

> Статус: **бумажный эксперимент**, 2026-10-13. Не контракт и не спека. Проверяет гипотезу из обсуждения [`../01-concept/spatial-model.md`](../01-concept/spatial-model.md) (§4.2, §6, §8.1, сценарии A–C из §10). Основание — наблюдение автора: собрать навык руками в текущем конструкторе не получилось, навык написал ИИ; язык проектирования техничен и заставляет прыгать между уровнями абстракции.

```text
Experiment:   Записать два существующих навыка так, как их рассказал бы человек
              (намерение · знание · повод · шаг · ожидание · обстоятельство · готово),
              и проверить, отображается ли каждая строка в элемент автомата без остатка.
Hypothesis:   Язык пространства навыка может отличаться от FSM словами и формой,
              но каждое его слово — ровно одна вещь автомата. Тогда нет второго источника
              истины и нет шага compile (урок E1). Единственное, чего не хватает модели, —
              имена знания на границах (контракт из spatial-model §6).
Purpose:      Понять, где именно рвётся поток проектирования и что минимально нужно
              добавить, чтобы человек мог написать навык, не покидая его уровня.
Material:     backend/scenarios/letter_agent_document.py (compose_letter),
              backend/scenarios/foreman_agent_document.py (process_foreman_request).
Procedure:    1) Записать навык человеческим языком. 2) Для каждой строки указать элемент FSM
              и то, где это знание живёт сегодня. 3) Отметить, что не легло, что язык
              вскрыл в самом навыке, и какие слова есть у человека, но нет у исполнения.
```

---

## 1. Нотация (рабочая, не окончательная)

```text
Навык: <имя>                    зачем: <одна строка>
Знает с начала: <имена знания>                       ← params + payload повода

Повод: <что случилось>                               ← событие из начального состояния
  приносит: <имена знания>                           ← payload события

  → <Шаг>                                            ← действие
      нужно:  <имена знания>                         ← вход действия
      узнаёт: <имена знания>                         ← выход действия
      <обстоятельство> → <шаг | ждать | готово>      ← переход с условием после шага

  → Ждать <чего>                                     ← состояние
      ждёт: <имена знания>                           ← payload ожидаемого события
      <обстоятельство> → ...

  готово [: <исход>]                                 ← final
  → <Шаг> (снова)                                    ← переход в уже существующее место
```

Четыре слова про знание — `приносит / нужно / узнаёт / ждёт` — единственное, чего нет в текущей модели как исполняемого контракта. Всё остальное — переименование того, что уже есть.

## 2. Письмо заказчику (`compose_letter`)

```text
Навык: Составить письмо              зачем: один фактор → черновик на столе → запись при факторе
Знает с начала: разговор, фактор, объект, захватка, работа, дни, даты, инструкция

Повод: стол просит письмо
  → Собрать черновик и показать человеку
      нужно:  всё, что знает с начала
      узнаёт: текст черновика
  → Ждать решения человека
      ждёт: решение, текст письма
      одобрил  → Записать письмо        → готово
      поправил → Отметить правку        → ждать дальше
      отложил  → Пометить отложенным    → ждать дальше
```

| Строка | Элемент автомата | Где это сегодня |
|---|---|---|
| Повод: стол просит письмо | `queued` → on `ui.request.parse_requested` | событие есть только как константа в `runtime/dispatcher.py`; в каталоге событий его нет |
| → Собрать черновик… | `transition.actions = [compose_draft]` | есть |
| нужно: всё с начала | `{{vars.object_name}}`, `{{vars.factor_title}}`, … в рецепте | пути в шаблонах; `vars` наполняется копированием payload (`runtime_service.py:130–134`) |
| узнаёт: текст черновика | `{{steps.write.result.structured.text}}` | обёртка `structured` известна только из кода инструмента; `outputSchema` действия пуст |
| → Ждать решения человека | state `waiting_for_human` | есть |
| ждёт: решение, текст письма | `payload.decision`, `payload.letter_text` | форма payload `human.request.reviewed` нигде не объявлена |
| одобрил → Записать → готово | guard `payload.decision == 'approve'`, actions `[record_letter]`, to `recorded` (final) | есть |
| поправил / отложил → ждать дальше | те же guard'ы, `to: waiting_for_human` (петля) | есть |

**Легло в нотацию.** Три состояния, четыре перехода совпали по числу с человеческой записью. Нового только `нужно / узнаёт / ждёт`. При этом «нужно» и «узнаёт» опираются на скрытые соглашения runtime (копирование payload в `vars`, путь `steps…structured…`), а не на объявленный контракт действия.

## 3. Заявка прораба (`process_foreman_request`)

Как записал бы человек:

```text
Навык: Разобрать заявку прораба      зачем: понять, что нужно прорабу, при необходимости уточнить
Знает с начала: разговор с прорабом, заявка (может не быть)

Повод: прораб написал
  приносит: текст сообщения

  → Разобрать заявку
      нужно:  текст сообщения
      узнаёт: нужно ли уточнение
      нужно уточнение → Спросить прораба
                            нужно: разговор с прорабом, что уточнить
                        → Ждать ответа прораба
                              прораб ответил → готово
      всё ясно        → готово
```

Как это лежит в автомате:

| Строка | Элемент автомата | Где это сегодня |
|---|---|---|
| Знает с начала | `params: request_id, conversation_id` | есть (`required` не проверяется при старте) |
| Повод: прораб написал | `NEW` → on `channel.message.received` | есть; имя события техническое, человеческого ярлыка у перехода нет |
| приносит: текст сообщения | `payload.text` → `vars.last_message` | скрытое правило runtime: `last_message` — алиас `payload.text` (`runtime_service.py:133–134`) |
| → Разобрать заявку | `transition.actions = [parse_request]`, `to: ANALYZING` | есть |
| нужно: текст сообщения | `input.text = {{vars.last_message}}` | путь в шаблоне, не контракт |
| узнаёт: нужно ли уточнение | `result.needs_clarification` | имя живёт только в коде заглушки `tools/llm/stub.py` и в строке guard |
| нужно уточнение → | `ANALYZING` on `action.parse_request.completed` guard `== true` → `CLARIFYING` | есть; **состояние `ANALYZING` и событие `completed` в языке невидимы** — см. правило R1 |
| всё ясно → готово | guard `== false` → `READY` (final) | есть |
| → Спросить прораба | `CLARIFYING.on_enter = [clarify]`, on `action.clarify.completed` → `WAITING_FOR_FOREMAN` | есть; **вторая форма записи того же** — см. R2 |
| нужно: разговор, что уточнить | `chat_id = {{vars.conversation_id}}`, `text = "Уточните… по грибкам?"` | вопрос зашит в рецепт; знания «что уточнить» нет нигде — см. D2 |
| → Ждать ответа прораба | state `WAITING_FOR_FOREMAN` | есть |
| прораб ответил → готово | on `channel.message.received` guard `payload.conversation_id == vars.conversation_id` → `READY` | guard — проверка тождества, не обстоятельство — см. D1 |
| готово | `READY` final | есть |

**Легло в нотацию с правилами.** Не везде «строка в элемент»: две строки отображаются через R1 и R2. Плюс скрытые соглашения runtime (`last_message`, guard на тождество разговора, результат заглушки LLM без `outputSchema`). Это не провал отображения — это предмет следующей проверки.

## 4. Правила отображения, которые пришлось ввести

**R1. Свёртка после шага.** Состояние, в которое ведут только переходы с действием X и из которого выходят только обработчики `action.X.completed`, показывается как *обстоятельства шага X*, а не как ожидание. В обратную сторону: шаг с обстоятельствами записывается в автомат именно так (действие на переходе → промежуточное состояние → обработчики `completed` с условиями); шаг без обстоятельств — просто действие на переходе.

Это единственное место, где одна фраза ≠ один элемент: фраза = действие + состояние + N переходов. Почему это всё же вид, а не компиляция:

- хранится по-прежнему только FSM;
- правило локальное и обратимое в обе стороны;
- автомат, не подходящий под правило (например, у `ANALYZING` есть ещё обработчик на другое событие), **всё равно отображается** — как явное ожидание «ждать: разбор заявки» с его ветками. Ничего непредставимого нет ни в одну сторону.

Behavior Graph (E1) нарушал последний пункт: в графе были конструкции без формы в FSM и наоборот, отсюда compile, lift и проверка эквивалентности.

Промежуточное состояние реально, а не фикция: run действительно отдыхает в нём, если действие ушло в ожидание человека (`on_failure: needs_human` → `_needs_human` → статус `waiting` уже после смены состояния, `skill_runner.py:47–49`). При жёсткой ошибке действия на переходе run остаётся в исходном состоянии со статусом `error`. Вид показывает промежуточное состояние только тогда, когда там есть что показать.

**R2. Одна фраза — одна каноническая форма.** «Спросить прораба → ждать ответа» одинаково звучит для `on_enter` целевого состояния и для действия на переходе. Язык читает обе формы, пишет одну (действие на переходе). Поведенческая разница между формами — где отдыхает run, если отправка не удалась, — в языке выражается обстоятельством («не удалось отправить → …»), которое автоматически выбирает форму с промежуточным состоянием (R1).

**R3. Возврат — ссылка, не узел.** «→ Разобрать заявку (снова)» — переход в уже существующее место. Отдельного слова для цикла не нужно (в Behavior Graph был особый вид ребра `loop`).

**R4. Знание именуется на границах.** `приносит` у повода и ожидания, `нужно / узнаёт` у шага, «знает с начала» у навыка. Где это живёт сегодня: `params` — есть; `outputSchema` команд инструментов — есть (плоские поля); `inputSchema / outputSchema` действия — поля есть, runtime не применяет; payload событий — в каталоге только имена `required_payload`, без типов, а событий стола (`ui.request.parse_requested`, `human.request.reviewed`) в каталоге нет вовсе.

**R5. Обстоятельство — выбор из известного.** Guard остаётся под капотом. Булево знание даёт две ветки («нужно уточнение / всё ясно»), перечисление — по ветке на значение («одобрил / поправил / отложил»), число — маленький выбор «равно / больше / меньше / пусто». Это не шире текущего guard-движка.

## 5. Что язык вскрыл в самих навыках (побочный результат)

Переписывание человеческим языком показало дефекты демо-навыка, которых на холсте не видно:

- **D1. Сантехника в навыке.** `payload.conversation_id == vars.conversation_id` — не обстоятельство, а проверка «тот ли это разговор». Для человека у неё нет фразы. Это работа runtime (D11/D12: run привязан к разговору, resume только по ожидаемому типу события), и из навыка она должна уйти.
- **D2. Незакрытое «нужно».** «Спросить прораба» требует знать, *что* уточнить, а ничего этого знания не производит — вопрос про грибки зашит в рецепт. В языке дыра видна как пустое `нужно`. В примере спеки это знание есть: `result.missing_fields`.
- **D3. Ответ не читают.** «прораб ответил → готово» в одну строку выглядит абсурдно: спросили и завершили, не разобрав ответ. В примере спеки правильно: «прораб ответил → Разобрать ответ (снова)».
- **D4. Знание без имени.** В `vars` копируются все ключи payload каждого события (`runtime_service.py:130–132`), результаты всех шагов сливаются туда же; `last_message` — алиас, о котором надо знать. `приносит / нужно / узнаёт` заменяют это явной привязкой.

Это то самое свойство из spatial-model §8.5: представление помогает обнаружить проблему, а не маскирует её.

## 6. Слова, которые есть у человека и которых нет у исполнения

Их **не добавлять в язык**, пока runtime их не умеет — иначе повторится E1.

| Человек говорит | Чего нет в runtime | Где это учтено |
|---|---|---|
| «если день нет ответа → напомнить» | таймер как источник события из DSL | research-questions C2 |
| «передать поставщику» (другому навыку) | композиция навыков; только через события мира | D20, ACTIONS §24 |
| «одновременно отправить и записать» | параллельные шаги | C5 (для человека «сделать A и B» читается так же — не критично) |

Когда runtime получит механизм, язык получает слово с тем же правилом «одно слово — одна вещь».

## 7. Observed results (бумага)

- Оба навыка **записались** человеческим языком. Формулировку «без остатка» смягчаем: они легли в нотацию **с помощью R1/R2** и **с опорой на скрытые соглашения** текущего runtime (копирование payload → `vars`, алиас `last_message`, необъявленный payload событий, пустые схемы действий).
- Потребовались два правила отображения (R1, R2) и одно добавление к модели (R4). Отдельный source of truth и шаг compile **в этих двух примерах** не понадобились — это ещё не доказательство обратимости.
- Человеческая запись короче автомата и вскрыла четыре дефекта демо-навыка (D1–D4).
- Гипотеза потока (ещё не проверена на новом навыке): навык можно набросать целиком на уровне обещаний (`нужно / узнаёт`), а рецепт отдать другому уровню / другому человеку / ИИ против контракта.

## 8. Interpretation (гипотезы, не выводы)

- Главный сдвиг вопроса: не «как должен выглядеть конструктор?», а **может ли человек описать поведение на одном уровне, оставив техническую реализацию другому?**
- Прыжки между уровнями, похоже, вызваны не самим автоматом, а **невидимым знанием** на границах. R4 (имена знания) — кандидат, не решение.
- Пространственная модель здесь потенциально глубже навигации: **разные уровни могут требовать разных языков**, а контракт между ними — возможность работать на своём уровне абстракции. Вывод «это только навигация над существующими сущностями» **преждевременен**; E5 его не доказал и не опроверг.
- Совпадение R4 с долгом runtime (REVIEW 2.4, 2.5; C6) — хороший знак, но скрытые соглашения из §2–§3 нужно сделать **предметом проверки**, а не предпосылкой успеха.

## 9. Открытые вопросы (перенесены в план ниже)

1. **R1 — вид или компиляция?** Промежуточное состояние как место отдыха run; достаточно ли условий из §4?
2. **Что видит обстоятельство?** Именование знания без коллизий (REVIEW 2.4).
3. **Фраза повода** — ярлык перехода или каталог событий?
4. **«Зачем» у шага** — отложить.

## 10. Согласованный порядок следующих экспериментов

Не смешивать две неизвестные: корректность языка навыка и организацию навыков на уровне агента.

| Шаг | Эксперимент | Критерий успеха |
|---|---|---|
| **1** | **E6 — обратимость R1/R2** | ✅ см. [`E6-skill-language-reversibility.md`](./E6-skill-language-reversibility.md): R1 ок; R2 ослабить; K5 — дыра |
| **2** | **E7 — навык с нуля** | Реальный сценарий без готового FSM; человеческое описание + входы/результаты действий; другой человек или ИИ собирает рецепт **без скрытых договорённостей** |
| **3** | **E8 — пространство агента** | `process_supplier_request` / жесты стола: появляется ли **самостоятельный язык** организации поведения или достаточно обзорной схемы (события → навыки → контракты) |

Цель порядка: понять не только, можно ли нарисовать систему красивее, но **какие новые возможности проектирования** даёт пространственная модель.

## Limitations

Бумага: ни один навык не был введён через новый язык и не исполнен. Выбор двух демо-навыков ограничен; оба короткие (3 и 5 состояний). Правила R1–R2 проверены на двух идиомах FSM; другие идиомы (несколько действий на переходе с разными исходами, несколько final, ошибка / `needs_human`) не проверялись. Скрытые соглашения runtime в таблицах §2–§3 ещё не отделены от «чистого» отображения.
