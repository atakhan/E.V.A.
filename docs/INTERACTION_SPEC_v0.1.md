# Interaction Specification
## Требования к архитектуре агента: человек, стол, голос, работа

> **Статус:** норматив слоя «акт человека → работа» (канон). Код: фазы 0–5 (pin, lock `conv-skill`, акт на проводе, таблица-диспетчер, snapshot/presence). Оговорки — в заметках. Честная приёмка §16 после фаз — [`INTERACTION_NOTES_ARCHITECTURE_REVIEW.md`](./INTERACTION_NOTES_ARCHITECTURE_REVIEW.md). Внедрение: [`INTERACTION_IMPLEMENTATION_PLAN.md`](./INTERACTION_IMPLEMENTATION_PLAN.md). Заметки: [`INTERACTION_IMPLEMENTATION_NOTES.md`](./INTERACTION_IMPLEMENTATION_NOTES.md).  
> **Не заменяет** [`SKILLS_SPEC_v0.1.md`](./SKILLS_SPEC_v0.1.md), [`RUNTIME_SPEC_v0.1.md`](./RUNTIME_SPEC_v0.1.md), [`EVENT_SPEC_v0.1.md`](./EVENT_SPEC_v0.1.md), [`ACTIONS_SPEC_v0.1.md`](./ACTIONS_SPEC_v0.1.md) **для исполнения уже выбранной работы**.  
> **Опора:** гладкость работы человека с агентом через веб-клиент (чат + рабочий стол + жесты).

Код v0.1 исполняет `Event → Skill Run → FSM → Action → Tool`. Этот документ фиксирует, чего **недостаточно**, чтобы агент ощущался коллегой за столом, а не двумя несвязанными ботами (чат vs кнопки).

При расхождении:

- **как исполняется уже выбранная работа** — RUNTIME / SKILLS / BEHAVIOR;
- **как человеческий акт становится работой, как устроены разговор, фокус и мир** — этот документ. Errata routing в RUNTIME — по [`INTERACTION_IMPLEMENTATION_PLAN.md`](./INTERACTION_IMPLEMENTATION_PLAN.md) фаза 0.

## 1. Принцип

Агент — не «умная болталка» и не набор кнопок. Человеку не нужно решать: «я сейчас в чате или в программе».

Три поверхности, один коллега:

```text
Стол        — правда дела (карточки, поля, статусы). Живёт в мире (веб-клиент / CRM).
Голос       — нить разговора. Спросить, поручить словами, поправить, ответить.
Присутствие — видно, чем агент занят и можно ли его дёрнуть.
```

Кнопки — не другой мир. Это короткие фразы, которые не хочется печатать: «разбери», «подтверди», «стоп».

```text
Человеческий акт (фраза | жест | входящее мира)
        + фокус
        + снимок стола
        + открытые работы
                ↓
        Диспетчер          ← этот документ
                ↓
        Skill Run(s)       ← SKILLS / BEHAVIOR / RUNTIME
                ↓
        Action → Tool
                ↓
        Эффекты: патч мира + голос + UI-предложение + присутствие
                ↓
        факты мира снова входят как Event
```

Skill по-прежнему не вызывает Tool напрямую. Event по-прежнему факт, не команда. Композиция «понял из чата и взял разбор» — обязанность **диспетчера**, не трюк внутри разговорного скилла.

## 2. Глоссарий

| Термин | Смысл | Не путать с |
|--------|--------|-------------|
| **Мир / стол** | Доменное состояние, которое видит человек | Историей чата, `vars` скилла |
| **Разговор** | Адрес нити: куда вернуть голос (`conversation_id` / web `sessionId`) | Скиллом, прогоном, карточкой |
| **Внимание / фокус** | Что человек имеет в виду *в этом акте*: selection, open card, вид | Разговором «навсегда» |
| **Работа** | Конкретное поручение в процессе (Skill Run + видимая задача) | Разговором |
| **Акт** | Фраза, жест UI или входящий факт мира, адресованный агенту | Типом события как выбором скилла |
| **Диспетчер** | Слой, который классифицирует акт относительно открытых работ, фокуса и стола | Event Router v0.1 (`event.type` → initial state) |
| **Жест** | Структурированное намерение в UI (кнопка на карточке, мультивыбор) | Отдельным каналом личности агента |
| **Эффект** | Пачка последствий поступка: мир + голос + UI + присутствие | «Только текст» или «только CRM» |

Веб `sessionId` = runtime `conversation_id`. Это адрес голоса, не «какая кнопка нажата».

## 3. R0 — сущности, которые нельзя склеивать

Из взаимодействия следует четыре разных адреса. Если два из них — одна строка в системе, ломаются параллельная работа, поправка на ходу и «это» с экрана.

| Сущность | Зачем человеку | В машине |
|----------|----------------|----------|
| Стол | Правда дела | Доменное состояние. Агент читает и патчит, не подменяет чатом |
| Разговор | «Верни голос сюда» | `correlation.conversation_id` |
| Внимание | «Это», «тот красный», открытая вкладка | Эфемерный `focus` на акте |
| Работа | Идёт / ждёт / отменяют | Skill Run; 0..N на одном разговоре |

**R0.** Корреляция обязана нести их **отдельно** и совместно: этот голос, эта работа, эта сущность, этот взгляд.

Следствие: кнопка «разобрать» и реплика в чате — не две сессии. Это два **входа** в один разговор, часто в разные работы, иногда в одну.

Связь с [`EVENT_SPEC` envelope](./EVENT_SPEC_v0.1.md): `conversation_id` и `skill_run_id` уже различны. Недостаёт явного фокуса и запрета трактовать «любое событие этой сессии» как resume единственного waiting-прогона.

## 4. Один мир

**R1.1 Стол — источник правды по делу.**  
Чат не хранит параллельную копию деловых полей. После правки на карточке любой следующий ответ агента читает стол.

**R1.2 Агент действует над тем же миром, что видит человек.**  
Поручение, которое меняет дело, не может закончиться одним текстом «готово» при мёртвых карточках. Молчаливый сдвиг стола без следа в голосе недопустим, если человек ждал ответ в разговоре.

**R1.3 Входящее извне попадает на стол**, не в отдельного бота. Сообщение канала — факт мира и появление/обновление сущности. Политика «сразу разбирать / спросить / ждать жеста» не создаёт вторую личность агента.

**R1.4 Runtime не обязан быть системой учёта.**  
Мир может жить в веб-клиенте. Платформа обязана: читать снимок, писать патчи, ждать факты мира. Канбан внутри скилла — не замена стола.

Граница согласована с [`RUNTIME_SPEC` §2](./RUNTIME_SPEC_v0.1.md): runtime не владеет долговременной бизнес-памятью. Этот документ требует **контракта с миром**, не переноса ERP в worker.

## 5. Два входа, одно намерение

**R2.1 Жест и фраза — равноправные входы в работу.**  
«Разбери новые» в чате и кнопка «Разобрать» сходятся в один класс работ, а не в две несвязанные машины.

**R2.2 Жест — структурированное намерение.**  
Кнопка на карточке = intent + объект(ы) + фокус. Текст = менее явный intent + тот же фокус, если он есть. Дальше диспетчер общий.

**R2.3 Согласие с предложением агента** («подтвердить эти три?» + подсветка) принимается и «да» в чате, и нажатием той же кнопки. Оба пути завершают **ту же** ожидающую работу.

## 6. Внимание

**R3.1 Клиент прикладывает фокус к любому человеческому акту.**  
Открытая сущность, мультивыбор, видимый вид/вкладка. Без этого «это» неразрешимо честно.

**R3.2 Фокус эфемерен и привязан к акту, не к разговору навсегда.**  
Сменили вкладку — следующее «этот» относится к новому взгляду. Старый фокус не липнет молча.

**R3.3 При двусмысленности агент переспрашивает коротко**, а не выбирает молча. Переспрос видим в присутствии.

**R3.4 Мультивыбор + речь — один акт.**  
«Эти подтверди, ту отложи» = один вход с набором объектов, не N отдельных диалогов.

Минимальный `focus` (клиент → агент):

```yaml
focus:
  view: requests            # что на экране
  openEntityId: REQ-17      # открытая карточка, если есть
  selectedEntityIds:        # мультивыбор
    - REQ-17
    - REQ-18
```

## 7. Диспетчер

Центральное требование. Очередной акт человека **не** является автоматически продолжением ждущей работы на том же `conversation_id`.

**R4.1 Классификация относительно открытых работ этого разговора, фокуса и стола:**

| Класс | Пример | Действие |
|--------|--------|----------|
| Ответ работе | «единица — мешки»; «да» на предложении | `resume` той работы |
| Поправка работе | «сначала Север» во время пакета | `amend` той работы, не слепой соседний прогон |
| Новая работа | «разбери новые»; кнопка на карточке | `start` соответствующего скилла |
| Вопрос мимо | «кто по арматуре?» пока идёт разбор | ответить, **не** снимая фоновую работу |
| Отмена / стоп | «стоп, не этому» | `cancel` / `redirect` указанной работы |
| Недоопределено | «подготовь на неделю» | сузить по столу, показать план, спросить ок или начать по политике |

**R4.2 Ждущий разговорный скилл не перехватывает чужие жесты** только потому, что совпал `conversation_id`. Ожидание «следующего сообщения» ≠ «любое событие этой сессии моё».

**R4.3 Текст не маршрутизируется одним `event.type`.**  
`channel.message.received` говорит, *что случилось*, не *какую работу начать*. Выбор скилла — функция `(текст, фокус, стол, открытые работы, политика агента)`.

**R4.4 Скилл остаётся процессом класса задач.**  
Диспетчер выбирает и стартует/возобновляет. Скилл не обязан быть универсальным NLU. Платформа обязана иметь слой **перед** «один event → unique initial-state match».

Это сужает наивное чтение [`RUNTIME_SPEC` §15](./RUNTIME_SPEC_v0.1.md) и pin waiting-run по одному `conversation_id`: такой pin допустим только если акт классифицирован как ответ/поправка **этой** работе.

## 8. Несколько работ на одном разговоре

**R5.1 Кардинальность: 1 разговор → 0..N работ одновременно.**  
Вопрос мимоходом не отменяет пакетный разбор. Отмена касается указанной работы (или явного «всё стоп»), не всего голоса.

**R5.2 Присутствие — проекция открытых работ.**  
Человек видит: занят / ждёт меня / простой; чем занят; можно ли дёрнуть. Обязательный выход runtime (живые Skill Run + человекочитаемый ярлык), не украшение UI.

**R5.3 Голос общий, прогресс — у работы.**  
Реплики могут ссылаться на работу. Состояние процесса не хранится только в истории чата.

**R5.4 Операции над работой, не только start:**

```text
start     — новая работа
resume    — акт = ответ ждущей работе
amend     — сузить очередь, сменить критерий на ходу
redirect  — стоп и смена объекта
cancel    — первоклассный жест, не авария
```

[`RUNTIME_SPEC` §20, §28](./RUNTIME_SPEC_v0.1.md) уже называют resume и cancellation. Для взаимодействия это **must**, не optional. `amend` / `redirect` — target этого документа.

## 9. Двойной эффект поступка

**R6.1 Поступок агента порождает пачку эффектов, не «или чат или CRM»:**

- патч мира (сущности, поля, статусы);
- опционально реплика в разговор;
- опционально предложение UI (подсветка, готовая кнопка, открыть карточку);
- обновление присутствия.

**R6.2 Контракт клиента принимает не только текст.**  
Сообщение без патча мира — норма для чистого вопроса. Поручение без патча мира — ошибка семантики.

**R6.3 Вопрос агента якорится на сущности.**  
«Нужна единица» видно на карточке **и** в чате. Ответ с любого входа (R2.3) закрывает один и тот же wait.

---

## 10. Стол побеждает кэш процесса

**R7.1 Ручная правка мира — факт**, на который работы опираются дальше (событие мира или свежий snapshot), а не `vars` с момента `start`.

**R7.2 Скилл не держит деловые поля как истину дольше одного шага**, если мир мог измениться. Перед «сказать сколько» и перед следующим `do` — читать стол.

---

## 11. Широкие поручения и разговор о процессе

**R8.1 Скилл может стартовать с неполными params.**  
Неполнота — штатный wait («вот 12, у двух нет объекта»), не отказ на входе.

**R8.2 План перед массовым действием — допустимый шаг процесса.**  
Человек утверждает план голосом или жестом (R2.3).

**R8.3 Аналитический вопрос читает тот же стол.**  
Не отдельный «мир для чата». Может закончиться поручением — тогда это новая работа из той же нити (R4).

---

## 12. Время и люди

**R9.1 Разговор и работы переживают закрытие вкладки.**  
«Ну что с сомнительными?» находит те же сущности и, если работы живы, те же прогоны. Если завершены — стол и исход, не пустой бот.

**R9.2 Акт имеет актёра.**  
Два голоса на одном столе могут конфликтовать. Конфликт — факт на сущности + правило (стоп / спросить / приоритет роли). Last-write-wins как единственная стратегия для «не брать» vs «подтвердить» запрещён.

## 13. Что остаётся в модели платформы

```text
Agent → Skills → Actions → Tools
Event → (Диспетчер) → Skill Run → FSM → Action → Tool → World → Event
```

**R10.1** Skill не зовёт tool напрямую.  
**R10.2** Skill не обязан звать другой skill, если диспетчер умеет стартовать соседнюю работу и связать её с разговором.  
**R10.3** Event остаётся фактом. «Нажали разобрать» — факт UI. Командует диспетчер + FSM.  
**R10.4** Веб-клиент — носитель стола, фокуса, жестов и отрисовки присутствия/предложений, не только транспорт чата.

Поведение одной работы задаётся FSM скилла ([`SKILLS_SPEC`](./SKILLS_SPEC_v0.1.md)). Этот документ не меняет states / guards / actions.

## 14. Контракт веб-клиента (минимум)

Клиент **отдаёт** на каждый акт:

```yaml
conversation_id: web:workspace:main   # куда вернуть голос
actor_id: user_42
focus:
  view: requests
  openEntityId: REQ-17
  selectedEntityIds: [REQ-17]
# жест:
intent: parse                         # стабильный id намерения
entity_ids: [REQ-17]
# или фраза:
text: "разбери это"
```

Клиент **принимает** от агента:

- текст в тот же разговор;
- патчи сущностей;
- `ui.proposal` (подсветить, предложить кнопку, открыть);
- снимок присутствия (живые работы).

Клиент отдаёт **чтение стола** (snapshot / context). Иначе R1 и R7 фикция.

Поля `sessionId` и исходящий `POST …/messages` из текущего web_client остаются. Их недостаточно: без `focus`, `intent`/`entity_ids`, патчей мира и присутствия контракт покрывает только кейс «сказал — ответил».

`skillId` на входе — **опциональная подсказка** диспетчеру, не единственный способ выбрать работу и не право перехватить чужой waiting-run. Жест и фраза сходятся по intent/фокусу; явный `skillId` не отменяет правило RUNTIME §15 (resume только если состояние ждёт этот event).

## 15. Вне scope

- Один скилл «на всё». Наоборот: много процессов, один диспетчер.
- Понимание любого текста без фокуса и без стола. Без R3 агент имеет право переспросить.
- Runtime как ERP.
- Чтобы каждая реплика была работой. Чистый вопрос — класс «мимо» из R4.

Planner как отдельный модуль приоритизации очереди работ по-прежнему открыт в концептуальной архитектуре. Диспетчер этого документа — классификация **очередного акта**, не глобальный планировщик.

---

## 16. Приёмка

Архитектура удовлетворяет документу, если на все шесть вопросов можно ответить «да»:

1. На одном разговоре идёт разбор, и одновременно можно спросить «кто по арматуре», не сорвав разбор?
2. Кнопка «разобрать» попадает в ту же семью работ, что фраза «разбери», с объектом из фокуса?
3. Ждущий чат **не** перехватывает клик по карточке только из‑за общего `conversation_id`?
4. Вопрос «не хватает единицы» виден на карточке и в чате и закрывается любым из двух ответов?
5. «Сначала Север» меняет уже идущий пакет, а не стартует слепой второй?
6. После ручной правки количества агент говорит новую цифру?

Пока на любой из шести «нет» — гладкость ещё не архитектура.

## 17. Трассировка к кейсам

Кейсы — мотивация требований, не контракт UI.

| Кейс (кратко) | Требования |
|---------------|------------|
| 1. Сказал — ответил | R4 класс «мимо», R6.2 текст без патча |
| 2. Ткнул в карточку | R2.1–R2.2, R6.1 |
| 3. «Это» про открытое | R3, R0 |
| 4. Фраза = кнопка | R2.1, R4.3 |
| 5. Поручил и сразу уточнил | R4.1 amend, R5.4 |
| 6. Вопрос с карточки, ответ в чате или на столе | R6.3, R2.3 |
| 7. Ручная правка | R1.1, R7 |
| 8. Мультивыбор + речь | R3.4 |
| 9. Вопрос пока идёт работа | R4.1 мимо, R5.1 |
| 10. Сменил экран, «этот» | R3.2–R3.3 |
| 11. Вернулся завтра | R9.1 |
| 12. Два человека | R9.2 |
| 13. Входящее само | R1.3 |
| 14. Стоп / не то | R5.4 cancel/redirect |
| 15. Поручение без объекта | R8.1–R8.2 |
| 16. Разговор о процессе | R8.3 |
| 17. Агент готовит жест на столе | R6.1 `ui.proposal`, R2.3 |
